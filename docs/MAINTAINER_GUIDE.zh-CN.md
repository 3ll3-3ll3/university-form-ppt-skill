# 中文维护说明

正式执行规则以根目录 `SKILL.md` 为唯一来源。本文件用于维护者快速理解当前工作流。

## 一次标准任务的执行顺序

1. 用户发送学校中文名、英文名、邮箱、邮箱域名、学院名或明显学校线索。
2. 直接识别学校，不询问“是否执行”。
3. 优先查学校官网、官方招生、官方国际交流、官方联系方式页面，核实中文正式名和官方英文全名。
4. 确定主要/代表性校区。多个校区时，经纬度最多输出两个最主要、最常见、最有代表性的校区。
5. 核实 Address、City、State/Province、Postal/Zip code 和对应校区经纬度。
6. 随机生成较短的二字/三字中文姓名并转拼音。字段约定：First name=姓拼音，Last name=名拼音。
7. 随机生成新的纯数字 Student ID，通常 7–8 位，不默认固定前缀。
8. 使用 `assets/certificate_template.pptx`（用户最后一次明确指定的最新模板）。
9. 只替换 `{{name}}`、`{{student_id}}`、`{{school_name}}`。
10. 第一行必须完整单行；换行时先换短姓名，再换短 Student ID，禁止改正文排版。
11. 第二行及之后必须自然连续顺排，不人为插入换行或硬拆词。
12. 右下角必须使用官方英文全名且保持单行；必要时只对该处做最小局部调整。
13. 若源模板含 `SAMPLE / NOT VALID` 或 `仅供演示，不具效力`，必须保持可见。
14. 实际渲染 PPT 为 PNG，逐项视觉验收。失败就重做并重新渲染。
15. 聊天交付顺序：真实 PNG → PPTX → 中文校名 → Official English Name → First name → Last name → Student ID → Address → City → State/Province → Postal/Zip code → 经纬度。
16. 每个表单字段单独代码块；默认不输出 Country/Region、Address line 2、VAT/GST ID。
17. 自动执行 Google Drive 归档，不等待用户二次提醒。
18. 按 `YYYY-MM-DD_HH-mm` 同名保存 MD/PPTX/PNG；同校同分钟冲突时追加 `_student_id`。
19. 先上传最终 PPTX/PNG，取得真实 URL 后写入 MD，再上传 MD。
20. 回读目标学校 Drive 文件夹，确认三件套存在后，才允许声称本次完整完成。

## 姓名与学号

### 姓名

- 正常二字/三字中国姓名；
- 优先短拼音组合；
- First name=姓拼音；
- Last name=名拼音；
- PPT `{{name}}`=`姓拼音 名拼音`；
- 绝不根据邮箱用户名猜真实姓名。

### Student ID

- 每次重新随机；
- 纯数字；
- 长度不是固定制度字段，而是服务版面；
- 通常 7–8 位；
- 默认无固定前缀；
- 第一行换行：先换短姓名，再缩短 Student ID，再渲染。

## PPT 修改原则

目标是“在原模板上只改三类占位符”，不是“重做一个相似 PPT”。优先直接编辑 PPTX XML。

正文区域禁止为适配第一行而修改字体、字号、颜色、行距、段距、文本框大小、文本框位置或正文位置。

必须保护页面尺寸、背景、图片、图形、日期、学院/系、专业以及所有其他非占位符内容。

右下角学校名例外：如果官方英文全名确实无法保持单行，只允许对这一处做最小必要宽度/位置/字间距/字号调整。

## 模板更新

用户上传新模板并明确要求“更改/更新模板”时：

1. 立即把该文件视为最新默认模板；
2. 同步替换 GitHub 的 `assets/certificate_template.pptx`；
3. 检查当前模板包含 1 个 `{{name}}`、1 个 `{{student_id}}`、2 个 `{{school_name}}`；
4. 检查源模板中存在的演示/无效标识在生成后仍被保留；
5. 同步更新 `assets/README.md` 中的模板 SHA-256；
6. 运行/更新模板测试；
7. 如果结构变化，同步修改脚本和规则。

注意：演示/无效标识是条件保留规则。新模板若本身不含某个标识，不应在测试中强制假定它存在。

## Google Drive 强制完成门槛

具体生成记录只放 Google Drive：

```text
大学PPT生成记录/<中文学校名>/
```

成功条件必须包括：PPTX 上传、PNG 上传、含真实链接的 MD 上传、目标文件夹回读确认。

本地生成三件套不代表归档完成；仅有 Drive 返回 URL 也不够，仍需回读确认。

如果任何一步失败，必须明确写 `该步骤当前没有成功完成。`，禁止假完成。

## REDO

发现任何错误时，必须完整重做到 Drive：PPT → PNG → 视觉验收 → 替换/更新 Drive PPTX → 替换/更新 Drive PNG → 更新 MD → 回读确认。

## 规则更新与 GitHub 同步

用户对工作流提出永久更改时，不能只在聊天里记住。按实际影响同步：

1. `SKILL.md`；
2. 英文文档；
3. 中文文档；
4. 实现脚本；
5. 测试；
6. 用户明确更换的模板。

只有真实 GitHub 写入成功后才能声称同步完成；任何未成功部分必须明确说明。
